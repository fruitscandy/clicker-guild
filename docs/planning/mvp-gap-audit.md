# 클릭커 길드 MVP 공백 조사 및 병렬 작업안

> 조사 기준: `main` 브랜치의 로컬 `HEAD` (`2bcc651`, 2026-08-09 확인)
> 제외 범위: 다른 PC에서 진행 중인 전투 세션의 그래픽, 전투 연출, 스킬 구현·다듬기
> 목적: 기술 스택이 아직 없는 상태에서 전투 외 MVP 필수 작업을 충돌 없이 병렬 착수하기 위한 기준

## 1. 현재 상태 요약

현재 저장소에는 실행 가능한 게임 프로젝트가 없다. 패키지 설정, 애플리케이션 진입점, 런타임 코드, 테스트, 빌드·배포 설정도 없다. 따라서 현재 자료는 게임 구현체가 아니라 **기획 초안과 실험용 그래픽 에셋 묶음**으로 보는 것이 정확하다.

확인된 자산은 다음과 같다.

- 길드원 25명의 이름, 등급, 직업, 공격 특징, 고유 스킬 이름
- 길드원 25명의 전신 캐릭터 콘셉트 이미지
- 첫 길드원 `견습 전사 로안`의 대기·이동·기본 공격·강타 애니메이션과 메타데이터
- 10단계 × 10스테이지의 몬스터 이름 초안
- 1단계 `초보자의 숲` 몬스터 10종의 콘셉트 이미지
- 에셋 생성 방향, 파일명, 일부 크기·기준점 규칙

아직 결정되거나 구현되지 않은 핵심 항목은 다음과 같다.

- 실행 환경과 기술 스택: 웹/데스크톱/모바일, 프레임워크, 렌더링 방식, 지원 브라우저·해상도
- 실제 게임 루프를 담을 코드와 데이터 구조
- 길드원 고용·보유·편성·강화 흐름
- 스테이지 해금과 보상, 재화 수급·소모, 성장 곡선
- 저장·불러오기, 버전 마이그레이션, 데이터 손상 복구
- 전투 전후 화면과 결과 반영 규칙
- 타이틀, 로비, 길드원, 스테이지 선택, 설정 등 비전투 UI
- 테스트, 빌드, 배포, 라이선스·출처 관리, 릴리스 체크리스트

현재 에셋은 모두 프로덕션 확정본이 아니다. 특히 1단계 몬스터는 1254×1254 PNG, 로안 애니메이션은 256×256 프레임이므로 런타임 규격과 로딩 정책이 정해진 뒤 별도 최적화가 필요하다.

## 2. MVP 범위와 우선순위

### P0 — 플레이 가능한 첫 빌드에 반드시 필요

1. **기술·제품 기준 확정**
   - 목표 플랫폼, 화면 비율, 입력 방식, 프레임워크, 실행·빌드 명령을 한 장으로 고정한다.
   - 첫 빌드 범위는 1단계 1-1~1-10, 로안 포함 최소 길드원 수, 사용하는 재화 수까지 명시한다.

2. **애플리케이션 골격과 화면 전환**
   - 실행 시 타이틀 또는 즉시 이어하기 화면이 보인다.
   - 로비/길드, 스테이지 선택, 전투 진입, 결과, 설정 화면 사이를 이동할 수 있다.
   - 전투 화면 자체는 다른 PC 작업을 연결할 자리만 제공한다.

3. **단일 게임 상태와 데이터 계약**
   - 플레이어 재화, 보유 길드원, 편성, 강화 수준, 스테이지 진행도, 설정을 하나의 명시적 상태 구조로 정의한다.
   - 길드원·몬스터·스테이지·보상 데이터는 화면과 로직에 하드코딩하지 않는다.
   - 전투 세션에는 `전투 입력 데이터`를 전달하고, `전투 결과 데이터`만 돌려받는 경계를 만든다.

4. **저장·불러오기와 초기화**
   - 자동 저장, 앱 재실행 후 복원, 새 게임, 손상된 저장 데이터의 안전한 초기화가 동작한다.
   - 저장 버전을 포함해 이후 구조 변경 시 최소한의 마이그레이션이 가능해야 한다.

5. **길드원 관리의 최소 기능**
   - 보유 목록, 상세 정보, 최대 4명 편성, 강화 또는 레벨업을 제공한다.
   - 고용 시스템을 넣는다면 MVP는 확정 고용 또는 단순 구매 중 하나로 제한하고, 복잡한 확률형 모집은 미룬다.

6. **진행·경제의 최소 규칙**
   - 1-1부터 1-10까지 해금 순서, 최초 클리어·반복 클리어 보상, 강화 비용을 데이터로 정의한다.
   - 보상 지급은 한 번만 처리되어 중복 클릭·새로고침으로 복제되지 않아야 한다.

7. **전투 전후 연결**
   - 선택한 스테이지와 편성 정보를 전투 세션에 넘긴다.
   - 승리/패배/중단 결과를 받아 진행도·보상을 정확히 반영한다.
   - 전투 세션이 아직 준비되지 않은 동안에는 가짜 결과 어댑터로 비전투 흐름을 독립 검증한다.

8. **최소 검증과 전달 가능 빌드**
   - 새 게임 → 편성 → 스테이지 선택 → 전투 → 결과 → 저장 → 재실행 흐름을 반복 검증한다.
   - 다른 PC가 동일한 명령으로 실행할 수 있도록 환경 준비와 실행법을 기록한다.

### P1 — MVP 안정성과 장르 경험을 높이는 항목

- 짧은 온보딩: 클릭 공격, 편성, 강화, 다음 스테이지 이동을 한 번씩 안내
- 오프라인 보상: 방치 보상이 제품 약속에 포함될 때만 제한 시간·상한과 함께 도입
- 길드원 고용 상점 또는 모집 화면
- 숫자 축약 표기, 다중 구매/강화, 부족 재화 안내
- 음량, 진동·화면 흔들림, 효과 강도, 데이터 초기화 설정
- 접근성: 키보드 조작, 포커스 표시, 색만으로 상태를 구분하지 않기, 모션 감소
- 저장 내보내기·가져오기 또는 복구 코드
- 에셋 매니페스트와 사전 로딩·실패 시 대체 이미지
- 기본 성능 측정과 오류 기록

### P2 — 첫 출시 이후로 미룰 항목

- 2~10단계의 전체 구현과 모든 몬스터 제작
- 25명 전원의 전투 애니메이션과 완전한 밸런싱
- 장비, 제작, 업적, 일일 퀘스트, 출석, 길드 시설 등 확장 메타
- 확률형 모집, 천장, 중복 캐릭터 처리
- 서버 계정, 클라우드 저장, 순위표, PvP, 소셜 기능
- 결제, 광고, 라이브 이벤트, 원격 밸런스 설정
- 다국어 전체 번역과 플랫폼별 상점 출시 자동화

## 3. 비전투 사용자 흐름

### 3.1 첫 실행

```text
앱 시작
→ 저장 데이터 확인
→ 저장 없음: 새 게임 생성
→ 짧은 소개/기본 설정
→ 초기 길드원 지급
→ 4인 편성 화면(첫 회는 로안 자동 편성 가능)
→ 1-1 선택
→ 전투 세션으로 이동
→ 결과 수신
→ 보상 지급 및 1-2 해금
→ 로비/강화 안내
```

### 3.2 재실행

```text
앱 시작
→ 저장 버전 검증 및 필요 시 마이그레이션
→ 정상 저장: 이어하기
→ 손상 저장: 복구 안내 후 백업/초기화 선택
→ (P1) 오프라인 보상 계산 및 수령
→ 마지막 안전 화면 또는 로비
```

### 3.3 일반 진행

```text
로비
├─ 길드원 목록 → 상세 → 강화/고용 → 편성 변경 → 로비
├─ 스테이지 선택 → 잠금/권장 정보 확인 → 전투 → 결과 → 다음/재도전/로비
└─ 설정 → 음량·접근성·데이터 관리 → 이전 화면
```

### 3.4 실패·예외

- 패배: 보상 지급 여부를 명확히 표시하고 재도전/강화/편성 변경으로 이동한다.
- 전투 중 이탈: 전투 시작 시점과 결과 확정 시점 중 어느 때 저장하는지 정책을 고정한다.
- 저장 실패: 플레이를 즉시 막지 말고 사용자에게 상태와 재시도 방법을 알린다.
- 콘텐츠·에셋 누락: 빈 화면 대신 안전한 기본값과 대체 이미지를 사용하고 오류를 남긴다.

### 4.3 콘텐츠

- 길드원은 이름과 특징만 있고 HP·공격력·공격 주기·성장 계수·고용/강화 비용이 없다.
- 고유 스킬은 이름만 있으며 배율, 대상, 발동 조건, 쿨다운, 지속 시간 등 데이터가 없다. 이 부분의 구현은 다른 PC 범위지만, 데이터 계약은 공동 합의가 필요하다.
- 몬스터는 이름과 이미지 중심이며 HP·방어·공격·보상·보스 규칙이 없다.
- 100개 스테이지 이름 초안은 있으나 MVP에 필요한 1단계의 수치, 해금 조건, 반복 보상이 없다.
- 시작 재화, 초기 지급 길드원, 첫 강화 비용, 예상 플레이 시간과 난이도 목표가 없다.
- 게임 제목, 한 줄 설명, 기본 용어(길드원/영웅, 단계/지역/스테이지 등)가 확정되지 않았다.
- 배경음·효과음·UI 아이콘·폰트와 그 라이선스 정보가 없다.

### 4.4 운영·품질

- 설치, 개발 실행, 테스트, 배포 절차가 없다.
- 지원 플랫폼·브라우저·최소 해상도와 성능 목표가 없다.
- 자동 검사, 스모크 테스트, 저장 회귀 테스트가 없다.
- 버전 번호, 변경 기록, 배포 산출물 명명 규칙이 없다.
- 외부 생성·구매 에셋의 출처, 라이선스, 생성 기록을 추적하는 목록이 없다.
- 개인정보 수집 여부, 분석·오류 기록 도입 여부가 정해지지 않았다.
- 출시 전 체크리스트와 알려진 문제 목록이 없다.

## 5. 의존관계와 권장 순서

```text
[D0 제품·기술 결정]
        │
        ├── [D1 프로젝트 골격]
        │       ├── [D4 앱 셸/화면 전환]
        │       └── [D9 빌드·자동 검사]
        │
        └── [D2 게임 데이터 계약]
                ├── [D3 저장·마이그레이션]
                ├── [D5 길드원/편성]
                ├── [D6 진행·경제 데이터]
                └── [D7 전투 입출력 계약]
                              │
                       [D8 결과·보상 통합]

[D4 + D5 + D6 + D8] → [D10 온보딩/설정] → [D11 전체 흐름 검증]
```

가장 큰 선행 조건은 D0이다. 플랫폼과 프레임워크를 모른 채 여러 에이전트가 코드를 만들면 합칠 수 없는 프로젝트가 생긴다. 단, D0이 결정되기 전에도 콘텐츠 수치 초안, 화면 상태표, 저장 필드 초안, 테스트 시나리오는 문서·중립 데이터 형식으로 병렬 작성할 수 있다.

전투 측과의 가장 중요한 공동 계약은 D7이다. 양쪽이 각자 화면과 전투 상태를 직접 공유하지 말고 다음 정도의 작은 경계만 합의한다.

- 입력: `stageId`, 편성된 `memberId`와 성장 정보, 설정, 전투 시작을 식별하는 고유 ID
- 출력: 고유 전투 ID, 승패/중단, 처치·소요 시간 등 요약, 계산된 보상 또는 보상 계산에 필요한 근거
- 원칙: 같은 전투 결과를 두 번 수신해도 보상은 한 번만 지급

## 6. 병렬화 가능한 티켓

아래 파일 경로는 기술 스택 확정 후 만들 **소유권 예약안**이다. 실제 폴더명이 달라져도 한 티켓이 소유한 경계를 유지한다. 각 작업자는 지정 범위 밖 파일을 수정하지 않고, 공용 파일 변경은 통합 담당자에게 요청한다.

### CG-00 제품·기술 결정 — P0, 최우선 단독 작업

- 작업: 목표 플랫폼, 기술 스택, 화면 크기, MVP 콘텐츠 수, 실행·빌드 방식, 용어를 결정한다.
- 완료 조건:
  - 한 명이 새 PC에서 문서만 보고 개발 환경을 준비할 수 있다.
  - 첫 빌드에 포함/제외할 기능이 체크리스트로 고정된다.
  - 전투 PC와 저장소·브랜치·통합 주기를 합의한다.
- 파일 소유 범위: `docs/planning/product-decisions.md`, `README.md`
- 병렬성: 다른 모든 구현의 선행 작업. 30~60분 내 타임박스 권장.

### CG-01 프로젝트 골격·실행 환경 — P0

- 선행: CG-00
- 작업: 선택한 기술로 최소 앱을 만들고 개발·빌드·검사 명령을 제공한다.
- 완료 조건:
  - 빈 환경에서 의존성 설치 후 앱이 실행된다.
  - 최소 프로덕션 빌드가 생성된다.
  - 환경별 비밀값 없이 로컬 실행이 가능하다.
- 파일 소유 범위: 저장소 루트의 패키지/빌드 설정, `src/app/**`, 정적 진입점
- 충돌 주의: 다른 PC가 이미 프로젝트 골격을 만들었다면 이 티켓은 즉시 중단하고 그쪽 결과를 기준으로 한다.

- 완료 조건:
  - 잘못된 ID·중복 ID·필수 필드 누락을 자동으로 탐지한다.
  - UI와 전투가 동일한 데이터 모델을 참조할 수 있다.

- 충돌 주의: 스킬 필드는 전투 PC와 공동 검토하되 실제 스킬 로직은 수정하지 않는다.

### CG-03 저장·복원·마이그레이션 — P0

## 7. 즉시 권장하는 병렬 배치

기술 스택이 아직 없으므로 첫 30~60분은 다음 두 줄로 제한한다.

1. 통합 담당 1명: CG-00 완료 및 다른 PC의 현재 브랜치·폴더 구조 확인
2. 조사 담당들: CG-02의 중립 데이터 초안, CG-06의 수치 초안, CG-11의 테스트 시나리오를 문서로 준비

CG-00과 다른 PC의 프로젝트 골격을 확인한 뒤에는 다음처럼 병렬화할 수 있다.

| 작업자/세션 | 1차 | 2차 |
|---|---|---|
| 통합 담당 | CG-01 또는 다른 PC 골격 채택 | CG-07 계약 병합, 전체 통합 |
| 세션 A | CG-02 데이터 계약 | CG-03 저장 |
| 세션 B | CG-04 앱 셸 | CG-05 길드원/편성 |
| 세션 C | CG-06 진행·경제 | CG-08 결과·보상 |
| 여유 세션 | CG-11 테스트 준비 | CG-09 또는 CG-10 |

전투 PC가 프로젝트 골격까지 이미 만들었다면 통합 담당은 CG-01을 새로 시작하지 않고 해당 브랜치의 골격을 가져온다. 이 확인 없이 별도 프레임워크를 생성하는 것이 현재 가장 큰 재작업 위험이다.

## 8. 다른 PC 작업과의 충돌 위험

### 매우 높음

- **루트 프로젝트 설정**: 양쪽에서 각자 프레임워크를 생성하면 병합보다 재구현이 빠를 정도로 충돌할 수 있다.
- **공용 게임 상태와 스킬/캐릭터 데이터 구조**: 전투 쪽과 비전투 쪽이 서로 다른 필드명·ID를 만들면 모든 화면과 저장 코드가 연쇄 수정된다.
- **전투 진입·종료 처리**: 양쪽이 보상 계산과 진행도 갱신을 모두 구현하면 중복 지급이 발생한다.

대응: 프로젝트 골격 소유자를 한 명으로 정하고, 데이터 계약과 전투 입출력 계약은 작은 공용 파일로 먼저 합의한다. **전투는 결과를 보고하고, 비전투 진행 시스템이 보상과 해금을 확정한다**는 단일 책임을 권장한다.

### 높음

- `docs/experimental-asset/guild-member-assets/roan-animation/**`
- `docs/experimental-asset/stage-01-beginners-forest/images/**`
- 전투 HUD, 스킬 버튼, 전투 캔버스, 이펙트·타이밍 파일

대응: 이 감사안의 작업자는 해당 경로를 읽기 전용으로 취급한다. 런타임 에셋이 필요하면 복사·변환 경로와 담당자를 먼저 합의하고, 원본은 그래픽 PC가 소유한다.

### 중간

- 길드원 스탯과 스킬 설명: 목록·강화 화면에도 필요하지만 전투 밸런스와 연결된다.
- 음량·화면 흔들림·효과 강도: 설정 UI는 비전투 담당, 실제 적용은 전투 담당이다.
- 스테이지·보상 데이터: 전투 난이도와 경제 성장 속도가 서로 영향을 준다.

대응: 비전투 쪽은 값 자체보다 스키마와 임시 기본값을 먼저 만들고, 임시값을 명확히 표시한다. 하루 1~2회 데이터 계약을 함께 검토한다.

### 낮음

- 저장 서비스, 로비, 길드원 관리 화면, 온보딩, 릴리스 문서와 테스트

대응: 파일 소유 범위를 지키면 독립 진행이 가능하다. 단, 저장 필드와 앱 셸의 공용 내비게이션 파일은 각 담당자 한 명만 수정한다.

## 9. 통합 규칙

- 작업마다 별도 브랜치 또는 worktree를 사용하고 동일 브랜치를 두 PC가 동시에 수정하지 않는다.
- 작업 시작 전 `소유 경로`, `읽기 전용 경로`, `공용 계약 파일`을 티켓에 기록한다.
- 커밋은 한 티켓의 한 완료 조건 단위로 작게 유지한다.
- 공용 계약 변경은 구현보다 먼저 병합하고, 양쪽 작업자가 그 커밋을 기준으로 갱신한다.
- 통합 담당만 루트 설정, 공용 상태 조립, 실제 전투 어댑터 연결을 병합한다.
- 최소 하루 두 번 또는 1~2시간 단위로 통합 빌드를 만들어 재작업을 조기에 발견한다.
- `main`은 항상 실행 가능 상태를 유지하고, 실험 중인 전투·그래픽 브랜치를 직접 합치지 않는다.

## 10. MVP 완료 판정

다음 시나리오가 대상 PC에서 연속으로 통과하면 전투 외 MVP가 완료된 것으로 본다.

1. 새 환경에서 설치·실행한다.
2. 새 게임을 시작해 초기 길드원을 확인하고 최대 4명 편성을 저장한다.
3. 1-1을 선택해 전투에 진입한다.
4. 승리 결과를 한 번 반영해 보상을 받고 1-2를 해금한다.
5. 보상으로 길드원을 강화하고 변경된 값이 전투 입력에 포함되는지 확인한다.
6. 앱을 종료·재실행해 재화, 편성, 강화, 진행도, 설정이 복원되는지 확인한다.
7. 같은 전투 결과를 다시 전달해도 보상이 중복 지급되지 않는지 확인한다.
8. 패배·중단·저장 손상·누락 에셋에서도 앱이 복구 가능한 상태를 유지하는지 확인한다.

이 기준이 통과하기 전에는 2단계 이후 콘텐츠, 전체 25명 애니메이션, 복잡한 모집·장비·업적 시스템을 추가하지 않는 것이 일정상 안전하다.
