# dongu(window) 앱 기록 추가 검토

이 문서는 NHN NAN 2026 제출용 AI 활용 기술 문서 취합을 위해 `dongu(window)`의 Codex 앱·ChatGPT 게임 제작 기록을 비식별 방식으로 정리한 자료다. 다른 팀원의 `desk64`, `note-pen`, `macOS` 자료와 분리하며, 중앙 취합자가 가져갈 내용과 중복 제거 기준을 기록한다.

## 1. 공개 범위와 제외 원칙

- 포함: 게임 기획, 기술 선택, 구현 지시, 인간 피드백, 테스트 결과, 공개 Issue·PR 번호, 외부 에셋·오픈소스 출처 보완점
- 제외: 시스템·개발자 지시, 내부 추론, 원시 도구 입출력, 로컬 절대경로, 실제 계정·장비 이름, 인증정보, 개인 연락·회사 관련 대화, 첨부 원본과 비공개 공유 URL
- 프롬프트는 개인정보가 없는 짧은 문장만 `정확 발췌`로 표시하고, 나머지는 여러 후속 대화를 합친 `비식별 재구성`으로 적었다.
- 아래 결과의 상태는 2026-08-10 앱 기록을 기준으로 한다. `merged`와 `review/unmerged`를 구분하며, 최종 제출 빌드 기준으로 다시 대조해야 한다.

## 2. NHN 요구사항에 바로 사용할 요약

[NAN 2026 안내](https://nan2026.nhn.com/)는 사전 과제를 “AI를 활용한 게임 제작”으로 설명하고, [참가 약관](https://nan2026.nhn.com/terms)은 사용한 주요 AI 도구와 활용 방식을 고지하도록 요구한다. 따라서 이 프로젝트의 기술 문서는 게임 내부에 생성형 AI API가 필수였다는 식으로 쓰기보다, **AI가 기획·구현·에셋 생성·검증·협업 조율에 어떻게 참여했고 사람이 어떤 판단으로 결과를 수정·승인했는지**를 설명하는 편이 정확하다.

### 2.1 AI 활용 구조

1. **기획과 범위 결정**
   - 대화형 AI로 2일 내 구현 가능한 장르, 브라우저 배포, 짧은 플레이 루프를 비교했다.
   - 생존·심리전 등 초기 시안은 구현 난이도와 피드백 속도 문제로 채택하지 않았고, 짧은 시간에 클릭·성장·영입이 반복되는 길드 경영 클리커로 방향을 좁혔다.
   - 채택된 핵심 루프는 `직접 공격 → 보상 → 무기 강화/길드원 영입 → 자동 전투 보조 → 다음 지역`이다.

2. **저장소 문맥 기반 구현**
   - Codex가 저장소 구조와 기존 동작을 먼저 읽고, GitHub Issue에서 작업 범위와 수정 경로를 선점한 뒤 독립 브랜치·작업공간에서 구현했다.
   - 기능 코드는 UI, 데이터 규칙, 오디오, 전투 상태, 저장 호환, 회귀 테스트를 함께 수정했다.
   - 진행 중인 다른 PR의 소유 범위를 침범한 사례는 즉시 복구하고, 해당 PR을 병합 대상에서 제외한 뒤 변경을 별도 PR로 분리했다. 이 사례는 AI 개발 프로세스의 오류 탐지·복구 근거로 사용할 수 있다.

3. **생성 에셋과 연출 제작**
   - 내장 이미지 생성 도구를 사용해 무기 15종, 무기 타격 VFX, 특수 공격 VFX 후보를 제작했다.
   - 공통 미술 지시를 고정하고 무기·스킬별 실루엣과 재질만 달리했으며, 투명 배경 WebP 변환과 용량 제한을 적용했다.
   - 생성물을 그대로 채택하지 않고 게임 화면에서 반복 검토했다. “단계별 효과 누적”, “그림판 같은 특수 공격”, “AI 기계음 같은 더빙”이라는 인간 피드백으로 구조를 폐기하거나 다시 생성했다.

4. **인간 주도 반복 피드백**
   - AI가 전용 로컬 미리보기와 테스트 상태를 준비하고, 사람이 실제 화면·녹화·소리를 검토했다.
   - 사람의 후속 지시로 여관 연출 속도, 고등급 사운드, 무기별 고유 이펙트, 광클 시 독립 재생, 오프닝 길이와 더빙 제거, 강화 노드 수와 가격, 전투 난이도 순서를 반복 조정했다.
   - 사용자의 명시적 병합 요청 전에는 브랜치에 유지하는 방식으로 승인 게이트를 두었다.

5. **검증과 병합**
   - 작업별 관련 테스트, 전체 Node 테스트, ESLint, production build, 데스크톱·모바일 브라우저 확인을 조합했다.
   - 밸런스 변경은 단순 수치 제안에 그치지 않고 30개 스테이지 또는 10개 지역 시뮬레이션으로 제한 시간과 성장 경로를 검증했다.
   - GitHub Issue·PR을 여러 AI 작업 세션의 공용 작업판과 변경 이력으로 사용했다.

## 3. AI 대상 주요 프롬프트와 지시 사항

### 3.1 정확 발췌

개인정보와 비공개 식별자가 없는 짧은 문장만 남겼다.

> “클리커류 게임 만들건데 길드 경영과 클리커를 접목할 수 있을까”

> “각 무기 단계마다 고유 이펙트가 있으면 좋겠어.”

> “업그레이드는 게임을 더 쉽고 빠르게 클리어해주는 부가요소”

위 문장들은 각각 장르 결합, 누적 효과 제거, 필수 성장과 선택 성장의 분리라는 실제 설계 원칙으로 이어졌다.

### 3.2 비식별 재구성 프롬프트

#### A. 여관 가챠와 판매

> 수동 영입을 1회·10회 가챠로 교체하라. 낮은 등급은 자주, 높은 등급은 드물게 등장하도록 확률을 공개하고, 10회 영입에는 할인 규칙을 둔다. 결과 카드는 순차적으로 등장시키며 고등급일수록 빛과 소리를 강화한다. 미편성 길드원은 등급별 가격으로 판매할 수 있지만 현재 파티원과 마지막 보유 캐릭터는 판매할 수 없게 하라. 브라우저 기본 확인창은 사용하지 말고 게임 세계관에 맞는 확인 UI를 제공하라.

#### B. 짧은 플레이에 맞는 성장 구조

> 기본 무기를 스테이지 재료에 맞춰 강화하면 선택 연구 없이도 모든 스테이지를 제한 시간 안에 완료할 수 있어야 한다. 1단계 무기만으로 전체 클리어되면 안 된다. 공격 범위·치명타·자동 공격·특수 공격·골드·길드원 공격력 연구는 더 빠르고 시원한 진행을 위한 선택 요소로 설계하고, 본관 승급 조건과 구형 저장 데이터 환급까지 함께 검증하라.

#### C. 무기 15종과 타격 VFX

> 전투 화면의 다크 판타지 톤에 맞춰 15개 무기의 실루엣과 재질을 모두 다르게 만든다. 공통 미술 지시는 두꺼운 차콜 외곽선, 조각된 재질, 따뜻한 대장간 림라이트, 절제된 속성광이다. 네온·마법진·과도한 폭발은 배제한다. 공격 효과는 하위 단계가 누적되는 방식이 아니라 무기마다 하나의 고유 궤적을 사용하고, 빠른 연속 클릭에서도 각 효과가 끝까지 독립 재생돼야 한다.

#### D. 오프닝 재연출

> 게임 실행 때마다 볼 수 있고 즉시 건너뛸 수 있는 짧은 오프닝을 만든다. 폐허가 된 길드, AI 코어의 복선, 길드 부활, 첫 길드원과 전투를 연결하되 웹 UI를 차례로 누르는 튜토리얼처럼 보이지 않게 한다. 임시 TTS가 기계 안내방송처럼 들리면 제거하고, 약 15초 자동 시네마틱과 빗소리·인장 파괴음·소환음·타이틀 타격음 중심으로 다시 구성한다.

#### E. 검증·협업 공통 지시

> 최신 main과 진행 중 Issue·PR의 수정 경로를 먼저 확인한다. 충돌 없는 독립 브랜치에서 구현하고 관련 테스트, 전체 회귀 테스트, lint, production build, 데스크톱·모바일 화면을 확인한다. 미리보기에서 사용자가 승인하기 전에는 병합하지 않는다. 다른 사람의 PR을 시험하는 경우 그 PR의 코드를 수정하거나 병합 대상에 포함하지 않는다.

### 3.3 프롬프트 설계의 특징

- 첫 지시는 목표와 감성 기준이 강했고, AI가 저장소를 분석해 영향 범위와 수치 초안을 제안했다.
- 후속 지시는 실제 화면에서 발견한 실패를 구체화했다. 예: “고급 등급처럼 보이지 않음”, “광클하면 중간에 끊김”, “TTS가 기계음처럼 들림”.
- 마지막 지시는 테스트와 병합 상태를 명시했다. 이 반복 구조는 `목표 → 구현 → 미리보기 → 인간 피드백 → 회귀 검증 → 승인 병합`이다.

무기 일러스트와 VFX는 기존 감사에서 `출처 없음` 또는 `부분 확인`으로 남은 항목이다. 위 프롬프트 정보는 보완 근거이지만, 모델·생성일·참조 이미지 권리·파일별 대응이 없으므로 `확인` 상태로 올리면 안 된다.

### 4.2 생성 음성과 음악

- 첫 오프닝에 적용했던 AI/TTS 음성 6개는 인간 검토에서 품질이 낮다고 판단되어 PR #103 최종 구성에서 제거됐다. 최종 제출 빌드에도 남아 있지 않은지 파일 목록과 런타임 참조를 다시 검사한다.
- Flow Music 전투 BGM 4곡은 기존 감사의 공개 원본 URL과 서비스 조건 보완 목록을 그대로 따른다. 이번 검토에서는 새 권리 근거를 확인하지 못했다.
- 프로젝트 자체 합성 WAV와 외부 효과음은 기존 `external-sources.md`의 파일·라이선스 표를 사용한다.

### 4.3 디자인 참고와 오픈소스

- 강화 UI를 간결하게 재설계할 때 [Tap Titans 2 스킬 트리 가이드](https://www.bluestacks.com/blog/game-guides/tap-titans-2/tt2-skill-tree-guide-en.html)와 [Cookie Clicker 업그레이드 설명](https://cookieclicker.fandom.com/wiki/Upgrades)을 참고했다. 이는 런타임에 포함된 에셋이 아니라 UI 정보 구조 참고 자료로 구분해 표기한다.
- 이번 추가 검토에서 새 런타임 오픈소스 패키지를 도입했다는 근거는 확인되지 않았다. 최종 OSS 표는 제출 빌드의 잠금 파일로 production 의존성만 다시 생성해야 한다.
- 기존 감사에 기록된 React, Next.js, vinext/Vite, Cloudflare 도구, Drizzle, TypeScript 등 직접 의존성과 전이 의존성의 라이선스 검토·SBOM 보완 요구는 여전히 유효하다.

## 5. 중앙 취합 시 중복 제거·상태 확인

1. `desk64`, `note-pen`, `macOS` 등 다른 기여 자료와 세션 제목이 같아도 PR·기능 영역이 같으면 한 사례로 합치고, 기여자별로 다른 인간 피드백만 보조 근거로 남긴다.
2. 기존 `desk64-001`~`desk64-011`과 이 문서의 사례를 PR 번호와 주제로 대조한다. 특히 PR #106 피날레와 시험 실행 기록은 기존 `desk64-009`와 중복될 수 있으므로 새 기능처럼 중복 기재하지 않는다.
3. `7448849` 특수 공격 후속은 기록 시점에 미병합이다. 최종 main에 들어갔는지 확인하기 전에는 완성 기능 목록에 넣지 않는다.
4. 최종 PDF의 외부 출처 장은 `external-sources.md`의 `부분 확인/미확인` 상태를 유지하고, 생성 대장·약관 사본·SBOM을 확보한 항목만 상태를 올린다.
5. 제출 직전 공개 저장소 전체에서 개인 식별 경로, 연락처, 인증 문자열, 비공개 URL을 다시 검색하고 사람이 최종 검토한다.
